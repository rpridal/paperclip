Pinned evidence: Paperclip base 9417b9ee1470c3b6f5e3c901d12150fa84534988; dark persistence PR https://github.com/rpridal/paperclip/pull/5, 56f0b17aa6eccf85a8af5e99abf3738e4b8dc2f8; runtime-platform source 050b3f792249800f6001b842f008273ecbdaf3b3. Žádný merge, grant, interaction, migrace dat ani rollout není součástí tohoto rozhodnutí.

## Rozhodnutí a mezera authority

Existující `authorizationService(db).decide` umí `issue:mutate`, `issue:comment` a `inbox:manage`. Je to authority pro existující issue operace a archivaci inboxu, NE důkaz genuine owner audience, oprávnění certifikovat source ani automaticky permission pro novou enqueue/delivery operaci. Vybraný minimální adapter má spojovat stávající evaluator, current source helper a strict parsing v jedné transakci. Pozitivní audience větev zatím nemá authoritative provider a MUSÍ vracet `owner_digest_source_authority_unavailable` bez ledger/queue zápisu. Dark tests mohou provider modelovat v izolované DB; testovací provider nesmí být production fallback.

Není nalezen existující serverový policy vztah, který klasifikuje konkrétní dokument/revizi a canonical otázky jako owner-reserved. `resolveInteractionPolicy` odvozuje resolver restrictions z požadavku, company cap a tool/secret governance; `human_only` říká kdo smí odpovědět, nikoli proč jde o owner otázku. Revision `createdBy*` říká kdo zapsal obsah, ne že smí certifikovat audience. Immutable ledger eviduje přesné odvozené binding, nikdy negrantuje authority.

Potřebné BOARD POLICY rozhodnutí (bez otevírání human interaction na této kartě): určit existující serverový action/resource vztah pro publikování authoritative question manifestu a minimální enqueue/materialize/delivery routing; určit publisher, chráněný source typ a policy revizi, která serverově klasifikuje otázky; potvrdit, že použití existujících issue mutation + responsible-user inbox policy je dovoleno pro routing, nikoli podkladové akce. Pokud takový vztah není ve stávající policy dostupný, pozitivní aktivace čeká. Nevytvářet permission key, allow bool, trusted agent whitelist ani ledger-grant API. Toto není žádost vlastníku o technické schválení; delivery owner musí otázku policy vyřešit v existující board governance/source práci.

Technické/provozní kroky zůstávají board formal approval nebo doložený standing trust. Kategorie personal_account, personal_credentials, money, irreversible_delete, host_decommission_with_data jsou jen syntax owner scope. Deploy přejmenovaný na money neprojde. Digest odpověď nenahrazuje action authorization ani deployment/delete gate.

## Vstup a serverová identita

Strict request `paperclip.owner_digest.adapter.v1`: `{version:1, originIssueId, source:{documentId,key,revisionId}, questionIds, idempotencyKey}`. Pro reviewed manual intake navíc `candidateAskIssueId` jako kandidát, ne authority. Neakceptovat principalId, runId, companyId, inboxUserId, producerPrincipalId, audience, approvalScope ani policy/receipt bool od klienta. Identifikátory zachovat přesně, žádné trimming/upgrading/defaulty; neznámá pole odmítnout.

Principal a company bere route z authenticated `req.actor`; agentní v1 vyžaduje run-bound JWT, shodu hlavičky s signed run a DB `heartbeat_runs` se stejným agent/company, running stavem a issue scope. Long-lived key samotný není v1 producer. Ověřit origin vůči skutečnému run scope, containment, checkout/mutation gates a cross-issue limit; idempotency je nikdy neobchází. `producerPrincipalId` je odvozený agent ID, ne nový system principal. Scheduler materialize později používá vlastní existující autorizovanou identity cestu, nikdy si nepůjčí origin run.

Inbox user se bere z aktuální serverové run identity (`heartbeat_runs.activeIdentityContextId`, `responsibleUserId`, `identityContextId` přes auth identity resolver), nikoli z title inboxu, prvního membera nebo textu dokumentu. V1 nepovoluje explicitní cross-user routing. Není-li právě tento user aktivním memberem stejné company, deny. `onBehalfOfMemberships` a memo před transakcí nesmí suplovat aktuální DB čtení. Owner audience znamená konkrétního policy-určeného vlastníka osobních dat, ne libovolného company role owner; potřebná source authority musí potvrdit shodu s odvozeným inbox userem. Chybí-li shoda, deny, nikoli změna adresáta.

## Authoritative source a canonical scope

Source identity se řeší `withOwnerDigestSourceRevision(tx, ...)`: origin -> documents -> issue_documents/document_revisions; attachment, company, latest_revision_id, latest body/format/revision number musí sedět. `documentId` a `key` z requestu se porovnají s výsledkem helperu, jsou jen selectors. Revize ASK popisu ani git SHA není revisionId; pouze DB UUID immutable origin dokumentu. Helper nyní nevrací authorship; adapter musí v téže transakci načíst revision `createdByAgentId/createdByUserId/createdByRunId` a existující policy provenance. Autor s obecnou document write permission není automaticky authoritative publisher.

Navazující existující source práce má dodat canonical manifest s verzí `paperclip.owner_digest.source.v1`, explicitními canonical otázkami a serverově ověřitelnou origin/revision/audience provenance. Obsah obsahuje questionSet `paperclip.question_set.v1`, nikoli obráceně. Přesný publisher-policy důkaz musí být uložen mimo agentem libovolně editovatelnou audience deklaraci a odkazovat aktuální policy verzi + source revision + question ID + skutečný reserved důvod + inbox user. Samotný podpis klientem/producera bez již schválené authority nestačí. Tato karta manifest nepřidává a nepředstírá existující registry.

Adapter bere canonical otázky výhradně z uzamčené authoritative revize. Požadovaný seznam musí být nonempty, bez duplicit, whitespace a unknown IDs; nesmí měnit option IDs, answerMode či význam otázky. Scope je jedna reserved kategorie; smíšené kategorie rozdělit do samostatných immutable položek, neměnit otázkám scope. Canonical pořadí je pořadí source manifestu, ne sort/normalizace tokenů. `answerScope={version:1,kind:'owner_only',approvalScope,revisionId,questionIds}` odvozuje server; exact JSONB comparison v ledgeru zůstává. Nová revize nebo jiná klasifikace vyžaduje nový binding a policy recheck, nikdy reuse staré autorizace.

Současný runtime-platform `parse_ask`, `question_id`, `question_payload`, `enqueue`, `read_mapping`, `answer` nejsou authoritative native source. Čtou title/popisy, generují q- IDs z ASK identifieru, zapisují presentation a komentářové mapování; to je kompatibilní legacy klient, ne authority pro tento adapter. Client audience/source změnu vlastní její stávající delivery, nikoli tento dokument.

## Existing policy rows, transakce a audit

Po kladném board policy mappingu adapter znovu volá EXISTUJÍCÍ evaluator na témže tx: `issue:mutate` na origin resource `{type:'issue',companyId,issueId}`, `inbox:manage` na tento resource se `scope:{userId:inboxUserId}`; pozdější origin komentář má zvlášť `issue:comment`. V1 nepoužije grant override pro cizí inbox. Výsledek evaluatoru je interní rozhodnutí s reason/evidence, nikoli caller `allowed:true`; samotný allowed výsledek bez source authority nestačí. Zachovat responsible-user intersection a trust/key boundary; shadow mode nelze vydávat za enforced povolení.

Existující řádky: `agents(id,company_id,status,permissions)`, `heartbeat_runs(id,agent_id,company_id,status,active_identity_context_id,responsible_user_id,context_snapshot)`, `run_identity_contexts(id,company_id,responsible_user_id)` přes existující resolver, `authUsers` (SQL tabulka `user`, sloupec `id`); `company_memberships(company_id,principal_type,principal_id,status,membership_role)` pro agenta i inbox usera, status active. `user_inbox_agent_policies(company_id,user_id,mode,allowed_agent_ids)`: responsible-user implicit open bez řádku je dnešní semantics, disabled deny, allowlist vyžaduje producer ID. Žádný nový row ani materialization defaultu. `principal_permission_grants(company_id,principal_type,principal_id,permission_key,scope)` je permission evidence jen pro skutečně použité existing branches evaluatoru, ne podmínka plošně pro všechny issue operace. Existující cross-user větev používá `inbox:manage` grant + `scopeAllows`, ale je mimo v1. `tasks:assign` opravňuje assignment, nikoli owner audience. `findGrant/decidePrincipalGrant` používají active membership a exact permission key; žádný `owner_digest:*` grant nevzniká. Audit musí uložit skutečné row IDs/versions a reason, i když rozhodnutí plyne z defaultu nebo role a neexistuje grant row.

Atomická revocation je implementační acceptance, NE dnešní vlastnost `access.decide`: současné policy reads a archive writer jsou oddělené; `inboxAgentPolicyService.update` dělá upsert, `setMemberPermissions` delete+insert. SHARE pouze na nalezeném policy/grant řádku nechrání ABSENCI default-open řádku ani grant insert. Bez společného protokolu je pozitivní adapter zakázán.

Minimální navržený protokol je coarse company fence: reader nejprve zamkne company row SHARE; všechny relevantní policy/identity revokace, membership/grant replace, inbox policy upsert/delete, agent termination a source authority policy změny musí nejprve zamknout stejný company row UPDATE. Bez zápisu grantu; tento fence je concurrency mechanismus, ne authority. Multi-company writer zamyká company IDs v stabilním pořadí. Pokrytí ALL těchto writerů musí být inventarizováno a testováno, včetně deletion/admin/compatibility cest, nikoli pouze HTTP route. Dokud to není hotové, adapter zůstane dark. Connection/ostatní revokace nepotřebují změnu, pokud nejsou součástí authority pro vybraný slice.

Po fence je pořadí: agents a run/identity context SHARE; active user owner membership rows před ostatními membership rows (ID pořadí, respektovat dnešní owner-first updateMemberAndPermissions), auth user a ostatní použité memberships SHARE; existující inbox policy a permission evidence SHARE; origin SHARE; documents SHARE; attachment+revision SHARE; authoritative policy evidence v jejím již existujícím writer pořadí; ledger SHARE; queue UPDATE; ASK/DIGEST carriers UPDATE v ID pořadí; origin blocker edge SHARE; interaction/receipt/delivery identity UPDATE. V1 source authority provider nesmí pořadí invertovat; pokud potřebuje jiné zámky, nutný samostatný lock-order důkaz před pozitivní větví. Run cancel/identity refresh a source doc upsert/delete musí respektovat stejný relativní pořádek; helper document-before-attachment neměnit. Nezamykat obří join s planner-selected order.

Všechny policy čtení po fence přes tx-bound nový evaluator/actor bez předtransakční memo cache. Unlocked discovery nikdy authority. Recheck current source i policy na enqueue retry, bind, present, answer/delivery; žádná transactionless authorize-then-write. Revocation-first = deny a žádný nový binding/queue/delivery write; operation-first = atomický commit před revokací, další retry deny. Persisted wait nesmí po revokaci ztratit admission protection a stát se orphanem; fail-closed quarantine bez promptu, uchovat provenance a odpovědi.

Successful mutation audit ve stejné transakci: contract version, actor/source/key metadata bez tokenu, agent/run/identity/company/inbox, source document/key/revision, exact canonical IDs/scope, policy decision reason a membership/grant/policy row IDs, queue/ASK/DIGEST/interaction IDs, idempotency key a outcome duplicate/new. Rollback nesmí zanechat success audit. Denial audit zvlášť po rollbacku s reason a target IDs, bez otázky/odpovědi/credentials v activity logu. Evidence je audit, nikdy následné oprávnění.

## ASK, DIGEST a verified receipt (navazující rozsah)

ASK se váže jednou přes existující `bindAsk`, pouze queued, unassigned todo same-company carrier, bez lease, s blocked origin a carrier-blocks-origin edge, bez interakce JAKÉHOKOLI statusu. Žádné title heuristiky. Duplicate bind nesmí obnovit stale carrier; všechny ordinary writers musí později respektovat carrier identity.

DIGEST presentation potřebuje nový explicitní immutable SERVER mapping: `{version:1,queueId,askIssueId,originIssueId,sourceRevisionId,questionId,digestIssueId,digestDocumentRevisionId,interactionId,inboxUserId,presentationGeneration}`. Digest document snapshot je current při materialize a zamkne se se všemi selected source revisions ve stabilním document ID pořadí. Mapování musí zahrnout každou canonical otázku přesně jednou; ID collisions mezi origin dokumenty vyřešit samostatným presentation ID s immutable canonical mapping, nepřejmenovat canonical IDs. `ask_user_questions` má requested/effective human_only a přesný addresseeUserId, serverově odvozený, žádný addresseeAgentId nebo toolAction. Revision target používá existující target/currentness mechanismus, nikoli plain comment mapping. V1 batch nejvýše 20 odpovědí, aby seděl stávající respond limit. Atomicky vytvořit interakci+mapping a změnit queue na presented; klíč reuse jen pro stejné payload/bindings. Několik původních dokumentů se neprohlásí za jeden origin.

Verified receipt je uložený výsledek existing authorized human respond path: interakce answered, `resolvedByUserId===inboxUserId`, resolvedByAgentId null, platná response audience/member policy při zápisu; receipt sváže interaction, digest target revision, presentation generation, canonical question/option IDs a exact odpověď. Nejde o client payload `{answered:true}`, text komentáře, wake summary ani queue lifecycle flag. Současný interaction row lze použít jako response evidence; dodatečná receipt/delivery identity je navazující persistence, v dark PR ještě není. Optional unanswered otázky zůstanou outstanding; expired/withdrawn/stale/pending interaction nikdy receipt. Agent zprostředkující delivery není human respondent.

Delivery znovu ověří existing action/resource policy, immutable mapping a current source. Scope/revision změna odmítne aplikaci staré odpovědi; uložený human receipt nezahodí, označí nonapplicable/quarantined pro řešení, neudělá tichý requeue s novým scope. Klíč delivery je exact `(queueId,sourceRevisionId,canonicalQuestionId,interactionId,presentationGeneration)` s payload equality; identický retry je no-op, odlišná odpověď stejným klíčem conflict. Origin comment, delivery receipt, queue completion a odstranění jen vlastního blocker edge jsou jedna transakce; wake je durable postcommit/outbox efekt s dedupe, ne předcommit side effect. Origin může zůstat blocked jinými edges; neobnovovat ho plošně. `answered` queue nastavovat teprve po kompletním ověřeném delivery, ne po prostém human respond. Deploy/delete musí i potom nezávisle autorizovat vlastní action.

## Reviewed manual compatibility intake a rollout hranice

Legitimate manual queued ASK zachovat, ale bez automatického povýšení textu na provenance. Stávající source delivery musí pro konkrétní manuální kandidát dodat authoritative origin document revision s canonical otázkami a policy evidence. Reviewed mapping explicitně sváže candidateAskIssueId -> origin/document/revision/question IDs/inbox. Obecný agent edit nebo board comment není typed source authority. Pro reviewed mapping platí stejné existing-policy a transakční revocation kontroly; ne vytvoření grantu ani approval podkladové akce. Pokud současná board policy neumí takový reviewed source zapisovat, compatibility positive intake čeká na výše pojmenované board rozhodnutí, není autodůvěra.

Před bind lock+recheck carrier todo, bez assignment/lease/ANY interaction, blocked origin a explicitní edge. Answered a již pending se nikdy nemigrují, nekopírují, nestahují, nepřeklasifikují. Chybějící provenance -> viditelný unresolved intake, ponechat legacy data; unknown nesmí dostat native admission exemption. Už typed queue v quarantine si ochranu zachová. Neprovádět plošnou migraci dle ASK prefixu, parent inboxu ani markeru komentáře.

První krok infra ve stejném dark paperclip worktree: tx adapter composuje current source helper + canonical validator + authenticated existing evaluator; výsledek rozliší denial missing authority od policy/revision/identity denial. Production provider absent => zero writer/caller; pozitivní fixtures pouze disposable DB. Testovat obě commit order revokace i default-row absence, stale/foreign/detached source, spoof principal/inbox/producer, mutable input, exact duplicate/conflicting key, technický scope maskovaný jako owner. Přidání ledger evidence je dovolené až PO authoritative decision a ve stejném commit; nevytvářet ledger-row policy endpoint.

Navazující delivery infra: společná recovery/wake/checkout admission pro queued/presented typed waits, ordinary ASK interaction pre-write denial (interaction count nezměněný), validované materialize + verified receipt/delivery + guard ordinary carrier writers + outbox, full PostgreSQL/HTTP gates a positive controls ordinary orphan, machine critical, doc revision review, formal approval. Source/client práce zůstává v runtime-platform vlastním worktree/PR bez instalace. Review nové service delty je oddělený úkol, tento dokument není verdict PR5.

Rollback: stop producer před downgrade; guard persisted typed rows funguje i s producer gate off; zachovat ledger/queue/receipt/origin edges, nedemotovat na orphan. Release/restart/install potřebuje zvláštní schválený pinned rollout. Rozhodovací karta může být done nyní; implementační prerequisite zůstává incomplete/dark.
