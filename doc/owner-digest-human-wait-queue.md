# Owner digest human-wait queue: dark persistence slice

This is not an enabled routing repair. The service is not exported from the service registry and has no HTTP, MCP, scheduler, recovery or client caller. No production writer populates the authorization table. No permission grants are created. Fixtures seed bindings only in disposable PostgreSQL. Do not enable a producer before the remaining boundaries are implemented and reviewed.

## Implemented

Additive version-1 owner_digest persistence with immutable company/origin/inbox/scope/producer identity. Existing bindings authorize exact JSONB scope, never a title, description or client boolean. Changed scope cannot reuse an old binding. Scope hashing is only an index accelerator: lookup compares exact JSONB and fails closed on a collision. Concurrent enqueue is insert-on-conflict plus exact readback. Lifecycle transitions use compare-and-swap and reject terminal overwrites. Authorization is checked even on duplicate operations, including origin company containment. Each service operation now runs in a transaction and holds PostgreSQL SHARE row locks on the origin and exact binding through commit. Binding DELETE/UPDATE and origin edits therefore serialize with enqueue/lifecycle writes: revocation-first denies without a queue mutation; mutation-first completes before revocation, and subsequent duplicate retries deny. This is atomic binding-ledger revocation only, not atomic revocation of a principal's membership, grants or audience policy; those still require the authenticated adapter before activation.

These rows are not approvals or standing trust. An answered lifecycle status is not an answer payload, delivery receipt or authority to deploy/delete. The service currently accepts server-internal producer identifiers; exposing it to an agent would be unsafe until an authenticated adapter maps its identity and checks existing policy. The binding ledger must not become an independent grant API.

## Dark ASK carrier identity

Migration 0287 adds a nullable ask_issue_id without backfilling earlier rows. The internal bindAsk operation assigns one distinct carrier once, after exact ledger authorization, under origin/binding SHARE locks, queue UPDATE lock and carrier UPDATE lock. First binding requires a same-company, unassigned todo carrier without checkout/execution lease, an already-blocked origin, an existing carrier-blocks-origin edge (held SHARE through commit), and no existing interaction of any status. Pending and answered legacy interactions are neither moved nor modified. A unique index prevents sharing one carrier between queue items; a trigger prevents replacing or clearing an established binding. Concurrent duplicate binds serialize. Enqueue explicitly projects its input fields so an untyped caller cannot inject ask_issue_id or lifecycle state.

This is identity persistence, not a reviewed compatibility intake, prompt guard, authorizer or admission exemption. It makes no title-based decision. Repeat binding rechecks ledger authorization but is only an identity retry; it is not authority to present, deliver, or revive a stale carrier. Carrier/origin/edge changes after binding are not yet prevented by all ordinary writers. Recovery/wake/checkout and interaction writers do not yet consult this field. Do not activate any caller until those shared boundaries and the authenticated versioned owner-only scope/revision contract are complete. The prior arbitrary JSONB scope is now rejected by the internal service on enqueue and every lifecycle/bind retry; it is not migrated or upgraded. A DIGEST carrier, pinned document revision and server-verified answer receipt remain separate work.

Generate retains five snapshots: adding 0287 prunes 0282_snapshot.json, with SQL/journal history preserved. The FK uses NO ACTION, not SET NULL: deleting a carrier cannot silently erase typed identity or turn it into orphan work. No production migration or rollout has been performed.

## Dark versioned answer-scope syntax

Internal operations require exactly version=1, kind=owner_only, approvalScope, revisionId and questionIds. approvalScope accepts the existing source producer categories personal_account, personal_credentials, money, irreversible_delete and host_decommission_with_data. Technical categories such as deploy are rejected even if a matching dark ledger row exists. questionIds must be nonempty, unique and whitespace-free; revisionId must be a UUID. Unknown fields, coercion, defaults, trimming and legacy upgrading are not allowed. Enqueue snapshots the validated object and nested IDs before asynchronous database work, so mutation of a caller object while waiting for a lock cannot change the authorized scope.

This is syntax containment, NOT authenticated audience policy. revisionId is syntax-checked, not yet resolved to a current issue document, and category text is not proof that a question is genuinely owner-reserved. An authenticated adapter must load the actual immutable source revision/question set, verify company/inbox membership and existing permissions/audience under atomic revocation, and record audit evidence before any binding producer is enabled. The runtime-platform source template remains unchanged; its reserved categories were inspected, not installed or adapted. Native v1 serialization still requires adapter contract review. Opaque preexisting rows are left byte-value unchanged and denied service mutation, not discarded or reclassified as ordinary orphans. No database CHECK constraint, backfill or new grant is introduced here. Explicit reviewed compatibility intake remains necessary for manually queued legacy work.

## Dark current-source revision boundary

withOwnerDigestSourceRevision resolves the specified revision through a same-company origin, issue-document attachment, document and document_revisions row. It requires latest_revision_id, body, format and revision number to match. It holds origin and source SHARE locks through a dependent internal operation in the same transaction; failures roll back that operation. It captures routing scalars before asynchronous work. A missing, detached, foreign or stale revision fails before the dependent writer. Both edit-first and reader-first commit orders are measured using pg_blocking_pids and commit barriers.

Source lock order is explicit: origin, document, then joined attachment/revision. Unlocked revision discovery is not authority; the final joined validation is pinned to the locked document and rechecks every identity/currentness predicate. A planner-selected attachment-first joined SHARE previously deadlocked with the real upsert writer's document-then-attachment updates. A controlled real-service regression reproduced the abort before the document-first lock fix. The ordinary delete writer also now locks only the document row (FOR UPDATE OF documents) before deleting attachments, matching upsert and source readers. Its separate controlled real-service test reproduced an attachment-first delete deadlock and now verifies both operations complete, cascading deletion is preserved and future source checks deny without calling the dependent writer. These are disposable PostgreSQL operations, not production deletes. No arbitrary callback retry or new authority is added.

This helper is dark and is NOT wired into enqueue/lifecycle, registry, HTTP, MCP or scheduler. Existing queue operations still perform syntax-only revision checks. The helper proves source identity/currentness only: document text/key is not trusted audience, a verified question set, approval, standing trust, policy authorizer or receipt. Future code must call dependent queue writes on the provided transaction, validate the actual versioned question-set contract and existing authenticated policy, then implement admission/materialize/delivery before activation. No source-template adaptation, legacy migration, schema change or new permission is part of this delta.

## Rollback and rollout

No feature activation is provided in this slice. Activation requires a separate default-off producer gate and guards that continue protecting persisted rows when that gate is off. Pause the producer before downgrading consumers. Preserve queue rows, answers and origin edges; never reinterpret a persisted typed wait as an orphan during downgrade. This migration contains no data backfill, title classification or changes to legacy interaction rows. A reviewed pinned-image rollout and any restart/install remain separate human approval steps.

## Validation scope

The focused PostgreSQL suite exercises persistence, enqueue retry races, lifecycle race rejection, routing immutability, exact-scope authorization, origin company containment and terminal handling. Lifecycle race tests hold the winning service transition in an uncommitted real transaction, observe the stale session's UPDATE blocked on that backend through pg_blocking_pids, then release the commit barrier. Both cancellation-first and presentation-first are tested; cancellation after a lost CAS must retry against the presented state. Promise start order and pg_sleep do not determine the winner. Removing the status CAS predicate makes both controlled-race tests fail, rather than silently accepting a terminal overwrite.
